# The three contradictions, settled live on 27 August 2026

Every claim below was produced by a request that ran. Where a result is a negative
("X does not filter"), it is gated by a control in the same session that produced the
positive, so the negative cannot be blamed on a misconfigured harness.

**The rig's licence had expired on 2026-08-18.** While expired, the metadata API kept
working on Basic auth but `POST /api/trusted-access/pull/tokens` returned 401

Embedding is licence-gated; source and metric CRUD is not. The valid key already
running on the two sibling rigs (expiry 2026-09-14) was applied via
`POST /api/license`, which cleared it.

**Test objects were disposable and isolated.** A new source
`zz-parity-throwaway-20260827` over `public.v_punch_monthly`, its own visuals,
dashboards and Trusted Access client. The `kimi` rig was chosen because its own
`BLOCKED.md` closed it out on 4 August as a dead-end model experiment; the

## 1. Custom metric write shape: both work, and Peter's 400 does not happen

Seven variants, one per row, each a real request against the throwaway source.

| # | Verb | Body | Result |
|---|---|---|---|
| 1 | `PUT .../custom-metrics/{name}` | `label`, `expression`, `dataType` | **201** |
| 2 | `POST .../custom-metrics` | `name`, `label`, `expression`, `visible` | **201** |
| 3 | `POST .../custom-metrics` | above plus `numberFormat` | **201** |
| 4 | `PUT .../custom-metrics/{name}` | `label`, `expression`, `dataType`, `numberFormat` | **201** |
| 5 | `PUT .../custom-metrics/{name}` | `label`, `expression`, `dataType`, `visible` | **201** |
| 6 | `PUT .../custom-metrics/{name}` | `name`, `label`, `expression`, `visible`, no `dataType` | **201** |
| 7 | `POST .../custom-metrics` | `label`, `expression`, `dataType`, no `name` | **201** |

Rows 4 and 5 are the ones Peter documents as HTTP 400. They return 201.

Four follow-ups pin down what the 201s actually mean, because an accepted field is
not necessarily an applied one:

* **`numberFormat` is applied, not swallowed.** Sent `{"type":"CURRENCY",
  "currencyCode":"GBP","decimals":4,...}`; read back `CURRENCY` / `GBP` / `decimals 4`
  on both the `POST` and the `PUT` path. A default-shaped format would have proved
  nothing, which is why a distinctive one was used.
* **`visible: false` is applied** and reads back `false`.
* **`dataType` is optional.** Row 6 omitted it and the stored metric came back
  `"dataType": "NUMBER"`.
* **`name` is optional on `POST`.** Row 7 omitted it and Composer derived
  `t1_peter_post` from the label `T1 Peter Post`.

The real difference between the two verbs is not which body they accept:

* **`PUT` is an upsert.** 201 when the name is new, 200 when it already exists.
* **`POST` is create-only.** A duplicate name returns 400 with
  `"Custom metric 't1b_nf_post' already exists"`.
* **`PUT` as an update replaces the whole resource.** Re-`PUT`ting a metric that had
  `CURRENCY`/`GBP`/4dp, with a body that omitted `numberFormat`, silently reverted it
  to `PLAIN`/2dp. This is the same partial-body overwrite that `SAFETY.md` records for
  `/api/users/{id}`, in a second endpoint.

## 2. Divide by zero: not null, and `CASE WHEN` is supported

The expression validator rejects real things, so acceptance is meaningful:
`sum(punch_count) / NULLIF(sum(shifts_worked), 0)` returns 400 with
`"Function 'NULLIF' not supported. Refer to Calculation Help for additional
information."` Amin's docstring is right that `NULLIF` is unavailable.

Accepted at create: plain division, division by a guaranteed-zero denominator,
`CASE WHEN ... THEN ... ELSE ... END` in upper case, the same in lower case, and
`COALESCE`.

Runtime, three KPI widgets on one dashboard so they share a query context:

| Expression | Renders |
|---|---|
| `sum(punch_count) / sum(shifts_worked)` | `2.00` |
| `sum(punch_count) / (sum(shifts_worked) - sum(shifts_worked))` | `Infinity`, period comparison `NaN` |
| `CASE WHEN (sum(shifts_worked) - sum(shifts_worked)) > 0 THEN sum(punch_count) / (sum(shifts_worked) - sum(shifts_worked)) ELSE 0 END` | `0.00` |

**The mechanism.** The SQL that reached Postgres for the divide-by-zero KPI was:

```sql
select count(*) as "mt__count",
       sum("ds"."punch_count") as "mt_ds_punch_count_sum",
       sum("ds"."shifts_worked") as "mt_ds_shifts_worked_sum"
from "public"."v_punch_monthly" as "ds"
where "ds"."punch_month" >= (timestamp '2026-07-31 23:59:59.999')
  and "ds"."punch_month" <= (timestamp '2026-08-31 23:59:59.999')
```

The division is absent. Composer pushes only the component aggregates down and
evaluates the arithmetic above SQL, so the result follows IEEE-754 float semantics,
not SQL three-valued logic. `x/0` is `Infinity` and `0/0` is `NaN`, and the KPI
renders those strings literally.

## 3. The confirmed-not-working list: all three hold

Tested through the real embed SDK (`/discovery/embed/embed.js`, 44,422 bytes) on a
same-origin host page, against a dashboard carrying a cross-source link labelled
`Site` mapped to `full_site_name`. Verdicts read from the SQL the query engine
generated, not from the rendered pixels.

**A. `dashboardComponent.trigger('EMBED/PUBLISH', ...)`: CONFIRMED broken.**
`typeof comp.trigger` is `undefined`. The component's full own-plus-prototype key
list contains no `trigger`; calling it throws `trigger is not a function`, the exact
error Peter recorded.

**B. `initialFilters` with `forTopic`: CONFIRMED accepted but inert.** Passed at
`createComponent` and stored verbatim on the component
(`comp.initialFilters` reads back the object). The bars query that followed:

```sql
... where "ds"."punch_month" >= ... and "ds"."punch_month" <= ...
group by "ds"."full_site_name" order by "ds_full_site_name" asc limit 20
```

No `full_site_name` predicate. Accepted, stored, ignored.

**C. `CustomEvent('EMBED/PUBLISH')` on `document`: CONFIRMED no effect.** Dispatched
at 12:58:00.939Z. No query of any kind reached the engine afterwards.

### The controls that make those negatives trustworthy

A negative result is only as good as the proof that the harness could have shown a
positive. Two ran in the same session, on the same dashboard and topic:

* `embedManager.publish("Site", {...IN ['Gulf Creek Copper Mine']})` produced
  `and "ds"."full_site_name" = 'Gulf Creek Copper Mine'` in the SQL, 0.9s later. The
  fieldLink, the topic label and the embed session were all therefore correct, so B
  and C failed on their own merits.
* `typeof embedManager.publish` is `function` and `typeof window.Zoomdata.publish` is
  `function`. Both documented working methods exist on this build.

### The item the previous verdict left open, now closed

`EMBEDDING_API.md` recorded, from static analysis of the SDK bundle, that the working
equivalent of C should be the SDK's own inner event, and flagged it as unproven end to
end for want of a dashboard and a source. It works:

```js
document.dispatchEvent(new CustomEvent("EMBED/CUSTOM_EVENT", {
  detail: { type: "EMBED/PUBLISH", data: { topic: "Site", message: {
    type: "selection", valueType: "ATTRIBUTE",
    ranges: [{ operation: 'IN', value: ['Karratha Gorge Iron Ore Mine'] }] }, options: {} } },
  bubbles: true
}));
```

Dispatched at 13:05:19.424Z; three queries carrying
`"ds"."full_site_name" = 'Karratha Gorge Iron Ore Mine'` reached the engine at
13:05:20.577Z, 13:05:20.582Z and 13:05:20.599Z.

## Incidental findings

Not part of the brief, recorded because each cost time and will recur.

* **`POST /api/export/visualdata/{id}` is unusable on the SI-bundled chart.** It
  returns 500 `"Couldn't get an endpoint for service sdk-service"`, and no
  `sdk-service` exists in any of the three rigs' service lists. There is no REST route
  to a visual's aggregated numbers in this deployment shape; the query path is the
  WebSocket.
* **`GET /api/sources/{id}/data` exists** and is marked experimental in the live
  OpenAPI at `/discovery/api-docs`. It returns raw rows only, with no aggregation and
  no custom metrics, so it cannot evaluate a metric.
* **`embed.js` needs `data-name="composer-embed-manager"` on its own script tag.**
  Without it the manager cannot locate its own `src` to derive the server path and
  `initComposerEmbedManager` throws `Cannot read properties of null (reading 'groups')`.
* **A proxy in front of Composer must forward WebSocket upgrades and must not strip
  `Content-Encoding` while passing gzipped bytes.** The first failure leaves every
  widget at `Reading 0% ...` for ever with no console error, which is the symptom
  already recorded at `LIMITATIONS.md:79`. The second delivers a corrupt `embed.js`
  whose only signal is `SyntaxError: Invalid or unexpected token`.
